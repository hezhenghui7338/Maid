# tasks Specification

## Purpose

描述挂在段上的任务记录、四态，以及用户可以改状态但不能改说明。来源是原 PRD 第 10 节；基数约束也对应原 PRD 第 7.4 节。

## Requirements

### Requirement: 一段至多一条任务

**来源**: PRD §7.4、§10

任务是段上的可选记录，带状态，不占用主题标签名额。每一段 MUST 至多一条任务。模型返回多条任务时，索引中的任务记录 MUST NOT 超过一条。没有嗅探出任务的段 MUST 没有任务记录。

#### Scenario: 两条任务不会都写入同一段

- **WHEN** 模型对一段返回两条任务
- **THEN** 该段索引中的任务记录不超过一条

### Requirement: 任务记录以原文为准

**来源**: PRD §10.1

一条任务 MUST 包含从该段识别出的任务说明、支撑判断的原文摘录、状态，以及是否由用户手改过状态。任务说明的事实来源 MUST 是原文。用户若要改变任务在说什么，MUST 修改原文并重新分析。任务面板 MUST NOT 改写任务说明。任务面板允许改的是状态和主题标签。

#### Scenario: 任务面板不能改写说明

- **WHEN** 用户在任务界面尝试修改任务说明
- **THEN** 说明保持分析时的内容

### Requirement: 任务只有四态

**来源**: PRD §10.2

正式状态 MUST 只有待确认、进行中、已完成、已取消。待确认表示模型认为这段像一项任务且用户尚未认可。进行中表示用户已认可、尚未做完，并入原文里的「未完成」，「执行中」改称此名。系统 MUST NOT 出现单独的「未完成」或「执行中」。用户 MUST 能按这四个状态筛选任务。把「待确认」改为「进行中」或保持「待确认」，就是确认该任务的落点。

#### Scenario: 分析与可选状态都只有四态

- **WHEN** 用户分析一篇会产出任务的文档，并查看可设置的状态
- **THEN** 出现的状态只有待确认、进行中、已完成、已取消
- **AND** 没有「未完成」或「执行中」

### Requirement: 无任务的段不进入状态筛选

**来源**: PRD §10.2

没有任务记录的段 MUST NOT 出现在按状态筛选的结果里。

#### Scenario: 空任务不进入筛选

- **WHEN** 一段的模型结果没有任务，且用户按任一状态筛选
- **THEN** 该段不出现

### Requirement: 手改状态写入索引

**来源**: PRD §10.3

用户 MUST 能把「待确认」改为「进行中」「已完成」或「已取消」，把「进行中」标为「已完成」或「已取消」，并在其余状态之间手动改状态。手改 MUST 写入索引，并记为用户手改。它 MUST NOT 写回 Markdown。

#### Scenario: 三种手改都留在索引里

- **WHEN** 用户把「待确认」改为「进行中」，把另一条「进行中」改为「已取消」，并把一条改为「已完成」
- **THEN** 三处变更都在索引中，并标为用户手改
- **AND** 对应 Markdown 字节不变
