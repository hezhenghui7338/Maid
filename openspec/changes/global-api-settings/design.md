# Design

## Context

见 proposal.md 的 Why。现在 `App.tsx` 把 API 设置读写成当前项目的 `.maid/settings.json`，未打开项目时拒绝保存。应用数据目录里已有 `state.json`（当前项目名），由 `create_project` / `remember_project` 整文件重写。项目索引仍在项目内的 `.maid/index.json`。界面测试用内存 `host`，不经过 Rust。

## Goals / Non-Goals

**Goals:**

- 全局设置与项目切换解耦，保存不要求已打开项目。
- 尚无全局文件时，用当前打开项目里已有的 `.maid/settings.json` 迁入一次。
- 迁入后项目内文件不再参与读取，也不会被新的保存写回去。

**Non-Goals:**

- 不提供按项目覆盖全局设置。
- 不删除已经落在项目里的旧 `settings.json`。
- 不改模型请求格式、默认 Ollama 地址，也不改 `decisions`。

## Decisions

1. **单独放在应用数据目录的 `settings.json`，不塞进 `state.json`。** `state.json` 每次记住当前项目都会整份覆盖。设置若和工作状态写在同一文件，切换项目可能把密钥丢掉。备选是扩 `StoreState` 并让每次写入都带上设置，多一处必须记得保留的字段。

2. **读取和迁移放在 Rust 命令里。** 新增 `load_settings(project)`：全局文件已存在则只读它；否则若传入的项目里有 `.maid/settings.json`，把它复制成全局文件并返回；两边都没有则返回默认值，且不创建全局文件。这样「还没保存过」和「已经迁入」可以区分，后打开的另一个项目仍有机会成为迁入来源。保存走 `save_settings`，只写全局文件。备选是前端自己 `readText` 项目文件再决定是否迁移，测试要复刻同一套分支，和桌面行为容易分叉。

3. **界面在启动时无项目加载全局设置，打开项目时再带上项目名调用一次 `load_settings`。** 保存按钮不再检查当前项目。分析继续用内存里的这份设置调用现有客户端。

4. **默认值不落盘。** 未保存、也无可迁移文件时只在界面使用 `defaultSettings`。一旦把默认值写成全局文件，之后就无法再迁入已有项目设置。

## Risks / Trade-offs

- [升级后先打开的那个带设置的项目会成为全局设置，其他项目里不同的密钥被忽略] → 与确认的迁入方式一致；设置界面仍可再改全局值。
- [旧项目里的密钥文件还在] → 不再读取、不再覆写。删除会在迁移失败时丢掉唯一副本。
- [界面测试的内存 host 必须实现同样的「有全局则忽略项目文件」] → 与 Rust 命令同一规则，并在两侧各锁一条：Vitest 锁界面沿用与分析请求，Rust 锁文件级迁移。

## Migration Plan

1. 用户升级后第一次打开仍带 `.maid/settings.json` 的项目，该文件被复制为应用数据目录的 `settings.json`。
2. 之后所有项目共用这一份。改全局设置不会改项目内旧文件。
3. 回退版本时，项目内旧文件还在；新版本写入的全局文件被旧版本忽略，各项目仍用自己的文件。
